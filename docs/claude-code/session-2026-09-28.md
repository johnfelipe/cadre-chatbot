     Plan: retry the escalation webhook once

     Context

     recordEscalation (lib/escalations.ts:70-82) makes one webhook POST with a
     3000 ms timeout. A transient Discord failure loses the notification, and
     only the log keeps it. Add one retry for transient failures.

     Changes

     lib/escalations.ts
     - Constants: WEBHOOK_TIMEOUT_MS = 1700, WEBHOOK_RETRY_DELAY_MS = 500. Worst
       case: 1700 + 500 + 1700 = 3900 ms, under 4 s.
     - New private helper postWebhook(url, escalation): Promise<void>. It loops
       over 2 attempts. Each attempt calls fetch with
       AbortSignal.timeout(WEBHOOK_TIMEOUT_MS) and the same body as today.
       - res.ok: return.
       - 4xx: log [escalation] webhook failed with id and status, return with no
         retry.
       - 5xx, or a throw (network error or timeout): if it is the first attempt,
         await a 500 ms setTimeout promise and retry. On the second attempt,
         log console.error("[escalation] webhook failed" | "webhook error", id, 
         status | error) and return.
     - recordEscalation calls await postWebhook(...) inside the existing if 
       (webhook). The helper catches everything, so it never throws.

     lib/escalations.test.ts (add to describe("recordEscalation"), using
     vi.useFakeTimers() and await vi.advanceTimersByTimeAsync(500); restore with
     vi.useRealTimers() in afterEach)
     - 5xx then 200: fetch is called 2 times and console.error is not called.
     - 400: fetch is called once, even after advancing the timers, and the error
       is logged.
     - 5xx twice: fetch is called twice, the error is logged, and the promise
       resolves.
     - Existing "never throws when the webhook fails" test (rejected fetch): it
       now retries, so it needs the fake timers too. It should assert 2 calls.

     plan.md (lines 122-123, Known limitations)
     Replace the "Discord is down" line with: the webhook is retried once after
     500 ms on a network error, timeout or 5xx (not on 4xx). If Discord is still
     down, the escalation is only in the logs, and the user still gets a
     confirmation. A queue with durable retries would close that gap.

     Verification

     npx vitest run lib/escalations.test.ts, then npm run lint && npm run 
     typecheck && npm test && npm run build. No npm run eval, since prompt and
     knowledge are unchanged. Commit as fix: retry the escalation webhook once 
     on transient failures.
